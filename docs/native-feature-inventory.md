### 迁移覆盖规则

- 桌面上的应用入口必须逐项在原生导航中有对应去处。
- `app` 是通用容器，不应与聊天、联系人等子功能重复计数。
- 设置内的隐藏子页面必须单独盘点，不能只迁移设置首页。
- 角色手机模拟器是角色的虚构手机内容模块，不等于本机系统电话/短信应用。
- CSS 美化导入不能直接执行任意网页 CSS；需要定义原生主题令牌、组件样式和受限扩展配置的映射。
- 本表只证明入口在源码中存在，不代表每个入口的完整业务行为已完成分析。

## 讯息 App（`v-msgs`）行为核验

已从上游 `msgRender` / `mgGen` / `mgAsk` / `mgAnswer` / `mgPass` 逻辑确认：讯息不是普通聊天列表，也不是 `app` 聊天页面的别名。它有两个独立标签：

- **传讯**：按当前用户资料和选定角色隔离短信记录。用户可以让角色主动生成一条老式功能机短信，也可以输入一句回复，再由角色生成回应；短信按角色筛选并保留历史。
- **匿名问答**：用户可以实名或匿名向角色提问，角色生成回答；也可以让角色模拟收取一批路人匿名问题并选择性回答；支持删除单条问题。
- 角色选择来自当前用户资料绑定的角色，若没有绑定角色则回退到未封禁角色；生成时使用角色系统提示词和该角色现有聊天上下文。
- 上游状态结构位于 `S.msgApp.by[用户资料 ID]`，每个用户资料有独立的 `box` 与 `qa` 数组。原生迁移应保留按用户资料、角色 ID 的隔离关系，短信和问答分别持久化。
- 原生实现必须继续使用已配置的模型/API，并处理无角色、无 API Key、请求失败、重复提交和进程重启后的记录恢复。不要把它实现成第二个聊天记录列表，也不要与聊天页面合并。

- `msgs` 已从纯占位页面升级为独立的“传讯 / 匿名问答”页面，接入现有 API 客户端和 Room 持久化；Room 从 v2 迁移到 v3，新增 `message_app_entries`，不清库。
